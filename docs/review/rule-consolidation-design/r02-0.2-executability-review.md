## 发现

### X-01 [MEDIUM] F2「12 处」仍不完整：再发现 4 处可执行后缀判定站点，且 `gui.go` 引用区间不含其同名函数

- disposition: **CORE_CORRECTIVE**
- 证据（均复核存在，且不在 F2 所列任一区间内）:
  - `internal/install/service.go:502-505` `requiresSystem7z`：`strings.HasSuffix(name, ".exe") && extractArchive`——与 `system7z.go:41` 是同一份可执行后缀知识，却是独立函数
  - `internal/install/runner_platform.go:139-143` `isExecutableForGOOS`：`ext := strings.ToLower(filepath.Ext(name))`，`return ext == ".exe"` / `ext != ".exe"`
  - `internal/install/runner_platform.go:184` `autoSelectOnlyWindowsExecutable`：`strings.EqualFold(filepath.Ext(candidate.ArchiveName), ".exe")`
  - `internal/install/gui.go:36-39` `DetectGUIInstallMode`：`switch filepath.Ext(lower) { case ".exe", ".msi": }`——F2 引用的 `gui.go:44-50` 是另一函数 `DetectInstallerKind`
- 影响: F2 已把 `runner_select.go:230-232`、`chooser.go:167` 这类「单条 `.exe` 比较」计入站点，同一标准下上述 4 处应一并计入（F2 计数应为 ≥16）。若这些 `.exe` 字面量留在 `runner_platform.go`/`service.go`，重复知识未消除，设计自述首要风险（`:22` 同伴规则漂移）仍残留；第 1 轮 R-02 的完整性要求未闭合。
- 建议: 在 F2 与迁移映射逐条补入并标注「迁往 filekind」；`isExecutableForGOOS`/`autoSelectOnlyWindowsExecutable` 改用 filekind 的折叠轴 API；`requiresSystem7z` 与 `shouldUseSystem7z` 的 `.exe` 分支合并为一处判定。

### X-02 [MEDIUM] 大小写轴只对 F3 组逐站点标注，F2 可执行后缀组的敏感/折叠归属未落文档

- disposition: **CORE_CORRECTIVE**
- 证据:
  - 设计 `:127` 对 F3 的 4 个站点已逐条标注大小写（`archiveExt` 折叠、`cacheAssetExt` 折叠、`extractor` 敏感、`json_index` 漂移变体）——这部分闭合 R-05。
  - 设计 `:128` 对 F2 可执行后缀组仅写「迁往 filekind」，未标注敏感/折叠。实测该组混合：`file_modes.go:54,56,76` 对原始 `file` 直接 `HasSuffix`（敏感）、`chooser.go:167`（base 来自不转小写的比较函数，敏感）vs `system7z.go:33`、`gui.go:44`、`runner_output.go:220-222`、`runner_select.go:226`、`runner_download.go:164`（先 `ToLower`，折叠）。
- 影响: 实现者若把 F2 组一律取 `XxxFold`，`file_modes.go`/`chooser.go` 对 `TOOL.EXE`、`TOOL.APPIMAGE` 的判定会改变；若一律取 `Xxx`，折叠侧会改变 —— 违反设计自述等价性（`:36`）。`:175`「逐个站点点建用例」提供护栏，但文档层面未固定归属，R-05 的文档交付项未闭合。
- 建议: 在迁移映射 F2 组补齐每站点的 `Xxx`/`XxxFold` 标注。

### X-03 [LOW] `internal/sdk/json_index.go:121-143` 的 `-tar.xz/-tar.gz/-zip` 归档后缀判定未纳入 F2/F3

- disposition: **CORE_CORRECTIVE**
- 证据: `internal/sdk/json_index.go:121-143` `parseNodeFileDescriptor` 用 `strings.HasSuffix(value, "-tar.xz")`、`"-tar.gz"`、`"-zip"` 判定归档类型（大小写敏感），是归档后缀知识的又一独立变体，未出现在 F2 的 12 处或 F3 的 4 份列表中（二者只列了 `json_index.go:224` 的 `archiveExt`）。
- 影响: 属同类知识的第 5 个表述；若目标是「归档格式只需改一处」，该站点会残留。因其使用 `-` 分隔且面向 node 索引的固定取值，可合理「刻意保留」，但文档应显式说明。
- 建议: 在 F2/F3 或迁移映射中点名该站点，注明「刻意保留并写明理由」或纳入 filekind。

### X-04 [LOW] D8 的「client 现仅依赖 stdlib」在包粒度不成立（结论「无环」仍正确）

- disposition: **CORE_CORRECTIVE**
- 证据: 设计 `:188`「防止 import cycle（`client` 现仅依赖 stdlib，`install` 已依赖 `client`）」。实测 `internal/client` 包导入 `internal/source/github`（`github.go:13`）、`internal/config`（`notices.go:13`、`http_client.go:9`）、`internal/cachemirror`、`internal/util`；仅 `cache_path.go` 一个文件是纯 stdlib。`install` 依赖 `client` 属实（`network.go:9`）。
- 影响: 不影响结论——新包只依赖 stdlib/util，任何现有消费者（含 `client`）指向它们都无环，Q2 的「`client → platform` 无环」成立。属事实陈述不精确。
- 建议: D8 改为「`client/cache_path.go` 现仅依赖 stdlib；整个 `client` 包依赖 `config`/`cachemirror`/`util`/`source/github`，均不依赖新包，故 `client → platform/filekind` 无环」。

## 结论

**PASS** —— 未发现任何 `CORE_BLOCKING`（无等价性被破坏的指令、无不可执行、无安全/数据/缺失功能/越权）。

关键可执行性结论（已验证为真）：

- 三个新包的职责与迁移映射**足以**表达各调用点现有策略而不改行为：`detect` 的 `{name,regex,anti,priority}`（`detectors.go:302-318`）可作数据，`systemOS.Match`/`systemDetector.Detect` 的 `:134-142,164-209` 策略留原地；`runner_platform.go` 的 `archSelectionPatterns`/`archiveNameMatchesPlatform`/`autoSelectWindowsMSVCAsset` 策略可留原地，仅消费 `platform` 数据；`extractor.go` 的「类型 → 构造函数」可分——构造函数（`NewTarArchive`/`NewZipArchive`/`NewSevenZipArchive`，`archive_formats.go:64,107,125`）与 gunzipper 闭包（`extractor.go:50-54`）均在 `install` 内，filekind 只需返回类型。
- import 方向无环：新包只依赖 stdlib/util；`install → client`（`network.go:9`）、`sdk → install`、`client → platform` 均无反向边。
- SR1301：用户输入路径保留 `regexp.Compile` 错误返回（`chooser.go:66`、`service.go:327`、`search_service.go:106`）；`MustCompile` 仅作用于 `QuoteMeta` 转义后的字面量（`tagfilter.go:46,49,51`、`service.go:338,344`），与设计 `:171` 一致。鉴权/资源归属校验不适用；秘密不进日志/仓库已核对；入参校验已核对。
- 因无 `CORE_BLOCKING`，不做 necessity proof；X-01~X-04 均为 `CORE_CORRECTIVE`，可在 plan 阶段以补表方式闭合，不阻断本轴。
